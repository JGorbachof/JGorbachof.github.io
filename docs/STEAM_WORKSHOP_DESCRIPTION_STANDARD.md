# Official Steam Workshop Description Standard
Creator-wide owner standard — revised 2026-11-21 (v10; closely related published editions, mandatory support links, natural-language credits)
Applies across Gorbachof original mods, compatibility patches, combined/replacement packs, ports, revivals and maintenance forks.

## WORKER ENTRYPOINT — MUST READ BEFORE WORKSHOP DESCRIPTION WORK
When the owner asks to write, revise, stage or publish any Steam Workshop description, read THIS document first. It overrides inherited boilerplate and older autogenerated description text.
- Use only real current mod/release information for features, game versions, requirements, interactions, credits and links.
- The section order is official. Do not fill out optional headings that offer no real player value.
- The public body uses Steam Workshop BBCode. Do not paste Markdown headings or authoring placeholders to Steam.
- Do not reintroduce retired sections, internal testing reports, developer updates or complicated attribution/permission explanations.
- HIGHEST-PRIORITY EDITORIAL RULE: Write as if prior development discussions, worker conversations, abandoned approaches, and unpublished adjacent work never occurred. A fact being prominent in project context does not make it relevant to a subscriber. Apply the standalone-reader gate below before including any sentence.
- PUBLIC RELEVANCE: Would an unfamiliar subscriber need this sentence to understand the published mod, use it, install it correctly, or avoid a real compatibility problem? If not, omit it. Never expose private development history, unpublished patches, unreleased editions, or internal plans.
- CREATOR CREDIT IDENTITY: Prefer the original creator's displayed Steam Workshop username (as on their original Workshop item), e.g. Anbeeld or Dingbat32. Never publish their real/legal names or parenthetical identity expansions, even if publicly searchable. If Steam username cannot be determined, use a verified public handle without guessing.
- RELEASED RELATED MODS: Link relevant original Workshop items, published standalone continuations, and directly related published alternative editions of the same mod family. When distinct editions offer subscribers different ways to use essentially the same product, link them reciprocally in their respective Related Mods sections. Keep the list small and helpful: no catalog-wide cross-promotion, adjacent-topic projects, unpublished branches, or speculative editions. This is navigational, not a dependency statement.
- MANDATORY CREATOR LINKS: Every published Workshop description includes a `Links` section with both the Gorbachof Modding Hub Discord and Gorbachof's GitHub. Read current URLs from `F:\CreatorHub\data\site.json` before preparing public copy. The GitHub entry is the owner's creator-wide **modding hub** link (`githubUrl`), not a source-code or mod-specific repository link. A mod's source repository is separate and must not replace the mandatory creator GitHub hub URL. Do not silently omit either link, even when an optional section is removed.
- PLAIN-LANGUAGE CREDITS: Thank original creators and meaningful contributors naturally using their verified public handles. A friendly, concise acknowledgment is preferred to legal, mechanical, or bureaucratic wording. Retain legally required notices inside the distributed files, not as promotional copy.

## Mandatory standalone-reader / context-isolation protocol — APPLY BEFORE DRAFTING

**Public descriptions are context-independent product pages, not compressed project conversations.** Write from the point of view of a first-time subscriber who knows nothing about prior questions, private discussions, implementation alternatives, earlier drafts, related workstreams or what the developer recently worried about. The published mod must make sense on its own.

**Separate factual evidence from editorial relevance.** Technical specifications, shipped files and release metadata may establish *what is true*. Only the current product and a new subscriber's concrete decisions establish *what deserves mentioning*. A discussion topic is never a relevance signal; repeated discussion, recency, owner curiosity, worker effort, and internal problem-solving never elevate a detail into Workshop copy.

Use this procedure, in order:
1. **Reset the framing.** Ignore the sequence of the conversation when choosing topics. Start with the current mod's name, shipped user-visible features, verified release version, direct installation requirements, actionable conflicts, appropriate source attribution, and the required public support links. Treat development conversations and worker notes as verification leads at most, not a narrative outline.
2. **Describe the product affirmatively.** Explain what the subscriber receives and what changes in their game. Do not write in response to an internal question, settle an old disagreement, compare against rejected plans, or defend a design choice. Do not add unsolicited "does not", "still requires", "is not intended to", "unlike", "no need for", or similar contrast/disclaimer copy.
3. **Gate every external reference.** Mention another project, mod, version, tool or prerequisite **only** when it is a verified direct install requirement, a real compatibility issue demanding user action, directly relevant source attribution, or an actually published closely related edition offered as an alternative in Related Mods. A casual conceptual connection, shared origin of an idea, or previously discussed comparison is not enough. Required links to the creator's Discord and GitHub remain mandatory.
4. **Write compatibility instructions only when actionable.** A compatibility sentence must tell the subscriber something they must install, remove, load in a particular order, or avoid because a verified material conflict exists. Do not proactively deny hypothetical incompatibilities or explain obvious distinctions. Missing support for an unrelated item is not inherently a known issue.
5. **Apply the cold-reader test sentence by sentence.** Without knowledge of any prior conversations, would this sentence be independently intelligible and useful to a prospective subscriber? Would removing it cause a real misunderstanding of functions, requirements, use, authorship, or actual compatibility? If not, delete it outright. Do not preserve it by adding background explanation.
6. **Perform a context-leak pass.** Look for gratuitous namedrops, defensive negations, historical asides, development vocabulary, unnecessary comparison, and details included because they were recently discussed. Delete them. Never use a specific developer anecdote as permanent policy wording; enforce this general principle instead.

**Exception is narrow and explicit:** A standalone description may naturally name a required dependency, an original published work, or a directly related published alternative edition in the appropriate requirements/links/credits section. This gives subscribers useful choices without narrating broader project relationships. Mandatory fields, relevant original/continuation/alternative-edition links, and creator Discord/GitHub links remain part of the official format.

**Fail-closed drafting rule:** If a candidate detail cannot be justified by an actual subscriber decision or understanding of the released product, **omit it**, even when verified true. Concision and completeness are measured against reader needs, not against how much project context a worker remembers.

**Original-mod continuation exception (owner, 2026-11-24):** For a standalone fork whose purpose is to maintain or update an older mod, place its Credits and Acknowledgments section immediately after the title and version information, before Overview. Move the existing acknowledgments intact; do not duplicate them at the bottom. This exception is exclusively for straightforward forks/revivals of older mods. New original projects, new compatibility editions and patches, combined packs, and projects merely using credited assets or contributions retain the usual end-of-description credits placement.

## Mandatory authoring rules — content and structure
1. ALWAYS begin with one large, bold mod title using `[h1][b]Exact Mod Title[/b][/h1]`, followed immediately by `Mod Version`, `Supported Game Version`, and `Overview`. No separate tagline, repeated title, or promotional preface.
2. Overview explains what changes and how the mod works, in natural language. NEVER add a separate How It Works section. Avoid parroting the feature bullets.
3. Features is for real, shipped, player-visible behavior. Prefer about 3–8 substantive bullet points for ordinary mods; longer, thoughtfully grouped lists are fine for major overhauls. Never pad to a number or dump every minor internal implementation detail.
4. Requirements must clearly state required DLC/other mods (including none, if applicable). Link parent/required mods directly when known. For a compatch, identify exact parent mods and required load order.
5. Compatibility should prioritize actionable information. Omit this entire section if there is truly nothing meaningful to say; never write empty 'compatible with everything' assurances. Put meaningful save-breakage or replacement instructions here, NOT in development notes.
6. Known Issues is ONLY for significant unresolved COMMUNITY-REPORTED issues. OMIT when none exist. No 'No known issues' filler. Internal QA findings and test narratives never belong here.
7. Bug Reports and Suggestions should be short, concrete, and not restate the Links section. Prefer the project's configured Discord support channel or actual issue tracker. If Links already suffice and there is no extra useful guidance, omit the standalone Bug Reports heading. **Links is never optional**: always include both the creator Discord and GitHub URLs. The canonical creator-wide URLs are in `F:\CreatorHub\data\site.json` (`discordUrl`, `githubUrl`). Use githubUrl from site.json as the creator-wide modding hub, with an appropriate hub label. Link source code only as a distinct, explicitly relevant resource when requested. Do not substitute original upstream repositories for the creator GitHub link. Verify both links exist and are correctly formatted before publishing.
8. Credits should only appear when attribution is useful (revivals, forks, contributors, source projects). Steam already shows the publisher; do not duplicate a 'Created by' line merely to fill space. Name original authors by their displayed Steam Workshop usernames (Steam handle takes priority over GitHub/Discord alias when they differ). **Write credits like a person thanking another person**: short, friendly, plain-language thanks that identify the actual contribution. Avoid legalese, license labels, mechanical attribution formulas, defensive justifications, and lengthy permission explanations. Example: 'Thanks to [Steam username] for creating [Original Project].' Preserve any mandatory legal notices separately in distributed files.
9. NEVER add Updates and Development, roadmaps, internal project status, future intentions, development logs, technical QA explanations, routine release notes/changelogs, or separate How It Works sections.
10. NEVER discuss internal/local/headless/server/automated/AI testing, test runs, test duration, benchmarks, logs or QA methodology in the public description. State accurate supported game versions without discussing how they were tested.
11. Never invent features, supported versions, compatibility assertions, community reports, credits, permissions or links. Use actual mod documentation and confirmed facts, not placeholders or guesses.
12. This is a short PLAYER GUIDE/PRODUCT DESCRIPTION, not a development diary. No hype, filler, repeated descriptions, or passive-aggressive disclaimers.

## Pre-publication relevance and privacy gate — mandatory
Review EVERY paragraph, feature bullet, compatibility claim and credit before staging or publishing:
- **Trivial implementation callouts:** Do not spotlight an incidental resource, minor supported item, low-level implementation detail, or narrowly scoped support fix unless it materially defines the mod's gameplay or solves a major user-visible problem. Something being new, discussed extensively or difficult to implement does not make it important enough for a Workshop bullet.
- **Unreleased and invisible projects:** Do not mention, name, compare with, or describe separate compatibility patches, unreleased mods, unpublished editions, unpublished updates, private versions or in-progress work. Players have not encountered these, and there is no useful public reference. Never say the user 'does not need' an unpublished patch.
- **Related editions versus unrelated variants:** Include only published mods that a subscriber would reasonably compare as ways to use the same underlying product or closely related component functionality. This includes the relevant original Workshop source(s), individual published components of a combination pack, and alternative published editions of the same mod (such as versions tailored to different mod ecosystems). When an alternative edition is relevant, its Workshop page should link back to the counterpart too. Do not link unrelated projects, every edition made by the author, hypothetical versions, or unreleased branches. This navigational exception belongs only in Related Mods; it does not authorize unsolicited comparisons in Overview, Features, or Compatibility.
- **Audience independence:** Write for a first-time visitor who knows nothing about private work, mod development conversations, internal compatibility experiments or creator shorthand. Explain only current shipped functionality, direct requirements, real actionable conflicts, appropriate attribution and support links. A sentence that derives its relevance from context outside the public product fails even if it is factually correct.
- **Credits identity protection:** Prefer each original author's displayed Steam username on the original Workshop item. Use another verified public handle only when no Steam username can be established. NO real/legal names, parenthetical legal-name expansions, inferred personal identities, or cross-referencing pseudonyms to real names. This prohibition holds regardless of public availability.
- **License compliance is separate from marketing copy:** Do not present generic license acronyms, license explanations, or 'MIT License' as a Workshop credit or selling point. Continue to retain any legally required license and copyright notice in the packaged mod or other legally appropriate distribution location. Never discard required notices just to simplify public prose.
- **Attribution tone:** 'Thanks to [Alias] for creating [Original Mod]' is sufficient. If specific permission is confirmed and relevant, 'Thanks to [Alias] for giving permission to continue [Project].' No defensive paragraphs.
- **Published-only external references:** In Related Mods, link applicable original Workshop publications, directly relevant published standalone components, and published alternate editions of the same mod family. Reciprocal alternate-edition cross-links are expected where both pages are editable. Distinguish navigation from requirements; never link a page to itself or treat a sibling edition as an install prerequisite unless that is independently true. Do not link development-only patches, invent URLs, or claim unpublished work was released.
- **BBCode integrity:** Check every [h2], [b], [list], [*], and [url=...] tag for valid syntax and matching closures. No escaped asterisk sequences, stray Markdown stars, trailing backslashes used as line breaks, Markdown links nested inside BBCode, malformed [url] tags, or nested bracket syntax corruption. Check text in an actual Steam-compatible preview/editor before publishing when practical.
- **No convenience exception:** Even if a claim is factually correct or discovered from internal project files, OMIT it when it does not serve prospective subscribers. Accuracy alone is not sufficient grounds for inclusion.

## Presentation rules — Steam Workshop BBCode
- Use exactly one `[h1][b]...[/b][/h1]` for the mod title at the very top, restrained `[h2]` section headings, `[b]` for short labels/feature names, `[list][*]...` for feature bullets, and `[url=https://...]Name[/url]` for actual links. Valve's Steam formatting help documents these tags.
- Do not repeat the mod title elsewhere as another heading or add giant banners, colored headline blocks, emoji, excessive capitalization, ASCII divider lines, or large gaps between paragraphs.
- Each section should be scannable. Keep Overview to roughly 1–2 short paragraphs for ordinary mods; concentrate the concrete differences in the Features list. Expand when a genuine full overhaul requires explanation, not just to make text longer.
- Screenshots and GIFs may demonstrate genuine gameplay (especially visual mods), but are optional. Prefer the Steam screenshot gallery; embed an image in the description only if it clearly helps explain a feature. Do not add decorative banner images by default.
- Link required Workshop mods directly, ideally with descriptive names. In Related Mods, cross-link applicable originals, direct published standalone components, and the closest published alternative editions of the SAME mod family; use reciprocal links when maintaining those editions. Always retain the separate `Links` section with actual Discord and GitHub links. Never publish raw placeholder URLs or bracketed authoring instructions, unreleased projects or unrelated specialist editions.
- Remove optional heading and content together. Preserve the relative order of any remaining headings.
- If the uploader only supports a smaller BBCode subset, use the supported equivalent while preserving structure and content.

## Appropriate variants without changing the canonical ordering
- Small utility / automation mod: one short Overview paragraph, concise features, real requirements, and only actionable compatibility or support links. No empty sections.
- Large gameplay overhaul: informative Overview plus grouped Features; dependency and compatibility guidance before support/credits. Do not bury player-critical details in a huge narrative.
- Compatibility patch: explicitly name and link required parents, explain what is made compatible, and provide exact load order. Do not turn the description into a technical conflict-resolution report.
- Combined replacement pack: plainly say whether parent mods must be installed or removed, and what functionality is included. Provide Related Mods navigation to the relevant originals, published standalone components, and any published alternate edition of the same combined product. These are NOT requirements unless separately documented as such. Avoid vague 'compatch' wording for a standalone replacement.
- Port / revival: link the original published Workshop item, credit its creator by displayed Steam username, and link the author's own published standalone continuation or closest published alternate edition when useful. Thank contributors naturally; accurately identify player-facing differences. Never expose personal/legal names.
- Alternative editions of one mod: list the relevant published counterpart(s) in Related Mods and ensure the counterpart descriptions link back. Label the choice with its actual public edition name; do not pad the Overview/Features with comparisons, defenses, or historical explanations. Link only variants a subscriber would realistically choose between.
